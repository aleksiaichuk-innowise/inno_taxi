Сверка `README.md` (техническое задание) с фактическим состоянием кода на `2026-09-09`. Легенда: ✅ выполнено · 🟡 частично / с отклонением · ❌ не выполнено · ➖ не применимо.

Каждая строка — по возможности с указанием, где смотреть в коде, и с честной пометкой, если реализация уже сознательно упрощена (см. `docs/superpowers/specs/*.md` — там для каждого отклонения есть обоснование).

| Сервис | По ТЗ | По факту |
|---|---|---|

| Order | Elasticsearch как основная БД, Gin+GraphQL, Redis-кэш заказов, React фронтенд | **Postgres** как основная БД (осознанно, см. spec — ES не подходит для строгого lifecycle), gRPC-Gateway вместо Gin+GraphQL, кэша нет, фронтенда нет |
| Analytic | ClickHouse, Kafka, Fiber | ✅ полностью соответствует |

| Gateway | NGINX, JWT через Auth, rate limiting | соответствует; тесты — только ручной `smoketest.sh`, не полноценный интеграционный сьют |

## Инфраструктура, DevOps и эксплуатация

Практически весь этот раздел ТЗ не затрагивался — фокус сессии был на бизнес-логике сервисов, а не на production-обвязке.

| Требование | Статус | Комментарий |
|---|---|---|
| Монорепозиторий с чёткими границами | ✅ | |
| Clean Architecture (3 слоя) | ✅ | в 4 из 6 сервисов с бизнес-логикой; `user_service`/`driver_service` — более плоская структура (задокументированное решение) |
| GitHub Flow (main/develop, feature-ветки, PR + review) | ❌ | всё коммитится напрямую в `main` |
| CI/CD (GitHub Actions: lint/tests/security scan/docker build) | ❌ | workflow-файлов нет |
| Docker Compose (dev) | ✅ | все 7 сервисов подняты и живо протестированы |
| Kubernetes + Helm (prod) | ❌ | |
| Конфигурация: .env + K8s ConfigMaps/Secrets | 🟡 | `.env`/env-переменные — да; K8s-манифестов нет |
| Документация: Swagger/OpenAPI, protobuf, GraphQL, диаграммы | 🟡 | protobuf — да (все Kafka/gRPC контракты); Swagger автогенерируется только для Order Service; GraphQL и архитектурные диаграммы отсутствуют |
| Unit / интеграционные / E2E тесты, Postman | 🟡 | unit + integration (dockertest) — да, по всем изменённым сервисам; E2E-сьюта и Postman-коллекций нет |
| golangci-lint, code coverage >80%, статический анализ | ❌ | используется только `go vet` вручную, без автоматизации |
| Мониторинг: Prometheus, structured logging, Jaeger | 🟡 | структурные логи (`slog`) — везде; метрик и трейсинга нет |
| TLS, K8s Secrets, регулярные security-аудиты | ❌ | весь трафик — plain HTTP внутри docker-сети |
| Circuit breaker, retry с backoff | ❌ | |
| Health-checks (liveness/readiness) в самих Go-сервисах | ❌ | healthcheck в compose есть только у инфраструктурных контейнеров (Postgres/Mongo/Kafka/…), не у самих Go-приложений |
| Таймауты на межсервисные HTTP-вызовы | 🟡 | новые gateway-клиенты (`order→wallet`, `order→driver`) используют `http.DefaultClient` без таймаута |
| Шифрование данных at rest / in transit | ❌ | |

## Взаимодействие между сервисами

| Требование | Статус | Комментарий |
|---|---|---|
| gRPC для синхронных вызовов | 🟡 | реализовано только в Order Service; остальные межсервисные вызовы (auth→user, order→wallet, order→driver, wallet-consumer и т.д.) — обычный HTTP |
| Kafka для асинхронных событий | 🟡 | `user_registered`, `order_created` — да; изменения статуса заказа и завершение платежа отдельными событиями не публикуются |
| Saga pattern для распределённых транзакций | 🟡 | компенсирующие действия реализованы вручную и точечно (charge/refund при отмене, claim/release водителя) — формального saga-оркестратора нет |
| Каждый сервис владеет своими данными, без прямого доступа к чужим БД | ✅ | |

## Итог

**Функциональные требования (7 сервисов, 53 пункта ТЗ)**: 30 выполнено полностью, 14 частично/с отклонением, 9 не выполнено — **≈70%** взвешенного покрытия (частичное = 0.5). *(Обновлено 2026-09-10: добавлены рейтинги поездок — `RateTrip` в Order Service, приём `order_rated` и агрегация `GET /analytics/ratings/drivers/{id}` в Analytic Service.)*

**Нефункциональные требования и инфраструктура**: закрыта только базовая часть (монорепо, Clean Architecture, Docker Compose, тестирование сервисного слоя, protobuf-контракты). Весь production-контур — CI/CD, Kubernetes, мониторинг/трейсинг, security-обвязка, saga/circuit-breaker — не затрагивался: это отдельный, гораздо более объёмный пласт работы, не пересекающийся с тем, что делалось в этой сессии (доведение бизнес-логики сервисов до рабочего состояния).

**Крупнейшие оставшиеся куски бизнес-функциональности**: вывод рейтинга на профиль User/Driver Service (данные уже есть в Analytic Service, не хватает межсервисного вызова для чтения), реальный матчинг по геолокации, Pricing Engine (дистанция/время/surge), accept/decline на стороне водителя, поиск через Elasticsearch, история/список заказов для райдера.
